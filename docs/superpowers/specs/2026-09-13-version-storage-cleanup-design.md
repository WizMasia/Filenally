# 버전 저장 공간 조회와 확인 기반 수동 정리

- 날짜: 2026-09-13
- 상위 이슈: [#12 파일 버전 관리 체계 구성](https://github.com/WizMasia/Filenally/issues/12)
- 기준: `main`, `2c2f5848a8042e29f6f212c6f7ebced2bef3a838` / v0.14.0
- 상태: 상세 설계 승인 완료(사용자: “구현 진행”). 구현 계획에 따라 착수.

## 1. 범위와 순서

이미 배포된 버전 캡처·목록·다운로드·복원·비교를 유지하면서, #12의 네 번째 범위인 저장 공간 조회와 명시적 수동 정리를 구현한다. 자동 보존 정책은 이 정리 경로를 검증한 뒤 다섯 번째 범위의 별도 설계·구현 계획으로 진행한다. 이 문서의 완료만으로 #12를 닫지 않는다.

산출물은 세 가지다.

1. 각 실제 보관 폴더의 등록 버전 수·논리 용량과 읽기 전용 저장 파일 검사.
2. 같은 보관 폴더의 선택한 버전만 미리보기·확인 후 영구 삭제하는 기능.
3. 삭제와 인덱스 갱신 사이에 중단된 작업을, 남은 파일을 추가 삭제하지 않고 정리하는 복구 기능.

추가하지 않는 기능: 자동 삭제, 보존 정책 설정, 압축·델타·중복 제거, 고아 파일 자동 삭제, `.trash` 정리, 원본 파일 삭제, 전체 디렉터리 재귀 삭제, 범용 손상 인덱스 복구, 별도 서버·데이터베이스·이력 시스템.

## 2. 선택한 접근과 대안

기존 `VersionStore`와 `VersionManager`를 확장하고 정리 의도를 버전 인덱스 v2 안에 기록한다. 정리 의도와 버전 목록을 한 번의 인덱스 쓰기로 함께 게시하여 별도 저널 파일 두 개를 맞추는 문제를 피한다.

대안인 파일 먼저 삭제 방식은 중단 후 사라진 파일을 정상 버전으로 표시할 수 있다. 인덱스에서 먼저 제거하는 방식은 파일 삭제 실패 시 사용자가 선택한 버전이 목록에서 사라진 채 남는다. 별도 저널 파일은 v1 독자가 진행 중인 정리를 무시할 수 있다. 따라서 v2의 진행 중 표시를 새 독자·작성자가 모두 이해하고, 구버전 앱은 지원하지 않는 스키마로 거부하도록 한다.

이는 여러 파일에 대한 원자적 트랜잭션이나 운영체제 잠금이 아니다. 정상 완료, 부분 완료, 복구 필요 상태를 구분하고 관찰 가능한 변경에 대해 중단하는 프로토콜이다.

## 3. 소유권과 불변 조건

- 모든 조회·정리는 실제 선택된 루트 핸들에 고정한다. 저장된 `fromSide`/`toSide`, 현재 동기화 방향, 이름이 같은 다른 폴더를 경로 결정에 사용하지 않는다.
- 한 번의 수동 정리는 하나의 루트, 1~100개의 중복 없는 등록 버전만 대상으로 한다. 두 루트에 걸친 선택은 실행 전에 거부한다.
- 삭제 경로는 검증된 ID와 원래 상대 경로로부터 `.filenally/versions/<id>/<originalPath>`를 재구성한다. 임의의 `storedPath` 문자열을 삭제 대상으로 신뢰하지 않는다.
- 정리 준비에서는 전체 인덱스의 캡처 ID가 `/^[a-z0-9-]+$/`에 맞는 단일 요소인지 추가 검사한다. 현행 UUID와 `profile-<timestamp>-<hex>` 대체 ID를 포함한다. 대소문자 별칭 등 서로 다른 기록이 같은 캡처 디렉터리를 가리킬 위험이 있는 보관함은 정리하지 않는다. 이 조건에 맞지 않는 기존 기록의 조회·복원 호환성은 그대로 유지한다. 선택 캡처 디렉터리의 실제 이름도 ID와 정확히 일치해야 한다.
- 현재 원본 파일, 다른 루트, `.trash`, 미선택 버전, 미등록 파일은 삭제하지 않는다. 부모 폴더를 재귀적으로 삭제하거나 비우지 않는다.
- 비어 있는 캡처 폴더와 경로 폴더는 남긴다. 이 범위의 용량 수치는 파일 본문의 논리 바이트이며 폴더 할당 공간을 포함하지 않는다.
- 기존 `.filenally` 강제 동기화 제외와 사용자 제외 목록을 유지한다. 설정 스키마 v2와 동기화 매니페스트·체크포인트를 변경하지 않는다.
- 사용자가 명시적으로 확인하기 전에는 권한 요청, 파일 생성·쓰기·삭제, 인덱스 업그레이드를 하지 않는다.
- 정리·복구에 필요한 핸들의 `isSameEntry`를 지원하지 않으면 쓰기 기능을 거부하고 읽기 전용 안내를 제공한다. 이름이나 크기만으로 핸들 정체성을 대신 판단하지 않는다.
- 수동 정리는 설정된 동기화 방향을 바꾸지 않는다. 다음 동기화는 기존 방향을 그대로 따른다.

## 4. 읽기 전용 사용량

### 빠른 집계

버전 관리자 새로고침에서 검증된 인덱스의 루트별 버전 수, 원래 경로 수, 기록된 크기의 합을 표시한다. 이를 실제 디스크 검사 결과로 부르지 않고 **등록된 버전 용량**으로 표시한다. 같은 원래 경로를 가진 버전들의 개수·용량을 집계하여 경로별 100행 페이지로 조회할 수 있게 한다.

한 루트의 인덱스 오류가 다른 루트의 정상 집계를 가리지 않는다. 실패한 루트의 값은 0이 아니라 확인 불가로 표시한다. 합계는 두 루트가 모두 검증되었을 때만 전체 합계로 표시한다.

크기는 유한한 비음수 안전 정수인지 확인한다. 잘못된 크기를 절댓값이나 0으로 교정하지 않는다. 합산은 `BigInt`를 사용하고 UI/API 경계에서는 십진 문자열을 사용하여 큰 합계의 반올림을 피한다. 이 규칙 때문에 유효하지 않은 집계는 기존 인덱스를 다시 쓰지 않는다.

### 명시적인 저장 파일 검사

사용자가 루트별 **저장 파일 검사**를 누르면 그 루트의 `.filenally`만 읽기 전용으로 순회한다. 인덱스 이외 파일의 본문을 읽거나 해시를 계산하지 않고 `File.size`를 사용한다.

다음 항목을 구분한다.

- 등록 경로에 실제로 존재하는 버전 파일 수·관찰된 바이트.
- 인덱스상 존재하지만 파일이 없거나 파일 종류(file/directory)·크기가 맞지 않는 버전.
- `versions/` 아래에서 인덱스 참조를 찾지 못한 파일. **미등록 파일**로 표시할 뿐 삭제 가능하다고 판단하지 않는다.
- 인덱스 파일 자체와 그 밖의 보관함 파일의 바이트.
- 검사한 시각, 읽기 오류, 순회 한도 또는 중지 여부.

인덱스가 없거나 손상되어도 접근 가능한 물리 파일의 관찰 용량은 표시할 수 있다. 다만 등록 여부·누락 판단은 확인 불가로 표시한다. 정상적인 빈 보관함과 손상된 보관함을 혼동하지 않는다. `.filenally`가 없으면 0으로 끝내되 만들지 않는다.

루트당 최대 100,000개 엔트리, 상대 깊이 256, 상대 경로 8,192 UTF-16 코드 단위로 순회를 제한한다. 반복형 순회를 사용하고 128개 엔트리마다 브라우저 작업 큐에 제어를 양보한다. 각 비동기 읽기 전후에 취소를 검사한다. 오류 상세는 최대 100개, 추가 오류는 개수만 표시한다. 검사 도중 한도·오류·중지에 도달하면 관찰분만 **부분 집계**로 표시하고 미방문 항목을 누락 파일로 판정하지 않는다.

인덱스와 루트 핸들을 검사 종료 시 재검증한다. 달라졌으면 결과를 오래된 스냅샷으로 표시하고 삭제 근거로 재사용하지 않는다. 전체 순회도 외부 프로그램 변경에 대한 원자적 스냅샷을 보장하지 않는다. 실제 디스크 할당량·압축률·여유 공간과 파일 크기 합계는 구분한다.

## 5. 인덱스 v2와 호환성

### 전환 시점

v1 보관함은 조회·다운로드·비교·복원 및 통상 캡처만으로 v2로 전환하지 않는다. 기존 신규 보관함도 계속 v1로 만든다. 첫 번째 수동 정리의 권한·확인·검증이 끝난 뒤에만 정리 의도를 포함한 v2 인덱스를 쓴다. 이후 캡처와 복원은 읽은 v2 형식을 그대로 유지하며 v1로 되돌리지 않는다.

v2의 최상위 필드는 `schemaVersion: 2`, `versions`, `cleanup`이다. `versions`의 레코드 형식과 경로·사유 규칙은 현행과 같다. `cleanup`은 평상시에 `null`, 정리 중에는 다음 정보를 가진다.

| 필드 | 규칙 |
|---|---|
| `id` | 비어 있지 않은 단일 안전 경로 요소인 작업 ID |
| `startedAt` | 유효한 ISO 8601 시각 |
| `remainingIds` | 현재 `versions`에 정확히 한 번씩 존재하는 1~100개의 서로 다른 ID |
| `completedCount` | 이 작업에서 인덱스까지 완료된 삭제 수, 0~100 |
| `completedBytes` | 완료된 삭제의 논리 바이트 합계인 비음수 십진 문자열 |

`completedCount + remainingIds.length`는 100 이하이다. 마지막 파일의 인덱스를 갱신할 때 `cleanup`을 `null`로 만들며 빈 `remainingIds`를 가진 진행 중 상태를 쓰지 않는다. v2의 알 수 없는 최상위·정리 필드, 잘못된 카운터, 중복 ID, 버전 목록 밖의 대상, 금지키는 거부한다. 손상된 v2를 빈 인덱스로 초기화하지 않는다.

`completedBytes`는 선행 0 없는 십진 문자열(0은 `"0"`)이고 최대 `100 × Number.MAX_SAFE_INTEGER`이다. `completedCount`가 0이면 바이트도 0이어야 한다. 숫자 변환 전에 문자열 길이와 형식을 제한하여 무제한 정수 파싱을 피한다. 모든 v2 레코드 크기는 비음수 안전 정수여야 한다.

인덱스 한도는 계속 5 MiB와 100,000개 버전이다. 정리 쓰기는 검증한 객체를 compact JSON으로 직렬화하여 의도 기록의 공간을 줄인다. 의도 추가 후에도 5 MiB를 넘으면 어떤 파일도 삭제하지 않고 선택 수를 줄이도록 안내한다. 한도를 자동으로 늘리거나 일부 대상만 몰래 처리하지 않는다.

### 구버전과 진행 중 상태

첫 정리 확인창에 **이 보관함은 업데이트된 앱이 필요하며 구버전으로 되돌릴 수 없음**을 명시한다. v0.14.0 이하의 v1 전용 앱은 v2 버전 조회·복원을 거부하고 캡처 기반 덮어쓰기를 완료할 수 없다. 구버전 캡처는 인덱스 검사 전에 본문을 기록하므로 미등록 캡처 파일을 더 남길 수 있다는 기존 동작도 문서화한다. 구버전의 모든 파일 쓰기를 막는다고 주장하지 않는다.

유효한 `cleanup`이 남은 루트에서는 새 앱의 정상 버전 목록·다운로드·비교·복원·새 정리 및 캡처 기반 덮어쓰기를 거부하고 복구 필요 상태를 표시한다. 읽기 전용 사용량 검사와 복구 준비는 허용한다. 다른 루트의 정상 데이터는 계속 표시한다. 버전을 만들지 않는 신규 파일 복사는 기존 규칙을 유지한다.

## 6. 수동 정리 준비와 확인

선택은 페이지를 넘어 유지하되 루트·ID에 결합한다. 전체 선택은 현재 페이지에서 같은 루트의 선택 가능한 행에만 적용하고 숨겨진 페이지를 선택하지 않는다. 한도는 100개이며 자동 분할 실행하지 않는다. 새로고침, 폴더 연결 변경, 관리자 종료 시 선택을 버린다.

준비는 인덱스 전체의 원본 내용과 핸들, 정규 레코드, 선택한 각 버전의 `File`·핸들을 고정한다. 인덱스가 정상이고 정리 중이 아니며, 선택한 각 항목이 실제 파일이고 기록된 크기와 맞는 경우에만 확인창을 연다. 경로가 없거나 파일 대신 디렉터리이면 정리를 준비하지 않는다. 기록된 MIME 유형과 보관 파일의 MIME 추정값이 다르다는 이유만으로 거부하지 않는다.

확인창에는 실제 보관 폴더, 선택 수, 경로·ID·캡처 시각·크기, 삭제 예정 논리 바이트, 영구 삭제 및 외부 백업 안내, v2 전환 여부를 표시한다. 현재 원본 파일은 삭제하지 않는다는 점도 표시한다.

같은 경로의 등록 버전을 전부 선택했다면 마지막 보관 버전 제거 경고와 별도 확인 체크를 요구한다. 해당 경로의 남길 버전이 실제로 유효한 파일인지 확인하지 못하면 마지막 버전 경고를 생략하지 않는다. 현재 원본이 있다는 이유로 마지막 보관 버전 경고를 면제하지 않는다.

마지막 버전 경고를 면제한 경로마다 실제 존재하며 기록 크기와 맞는 미선택 버전 하나의 레코드·핸들·메타데이터를 준비 토큰에 고정한다. 실행 전과 해당 경로의 각 삭제 직전에 그 보존 근거를 다시 검증한다. 달라졌으면 삭제하지 않고 경고를 포함한 새 확인을 요구한다. 보관 파일의 과거 무결성 해시는 없으므로 이 존재·크기 검사를 과거 바이트 무결성 보장으로 표현하지 않는다.

취소·Escape·닫기는 쓰기와 권한 요청 없이 준비된 `File` 참조 및 확인 토큰을 버린다. 확인 토큰은 `WeakMap`에 등록한 단일 사용 객체로 만들며 외부에서 임의 구성한 객체는 실행할 수 없다. 준비 결과가 늦게 도착해도 닫거나 교체한 화면을 다시 열지 않는다.

## 7. 삭제 실행 프로토콜

```text
읽기 전용 준비 → 사용자 확인·권한 → 전체 재검증
  → v2 정리 의도 쓰기·close·읽기 확인
  → [선택 파일 재검증 → 파일 하나 삭제 → 인덱스에서 해당 기록 제거·close·읽기 확인]
  → 마지막 항목과 함께 정리 의도 해제
```

1. 확인 클릭에서 실제 보관 루트의 `readwrite` 권한 요청을 시작한다. 저장 계층에서도 권한이 `granted`인지 확인한다. 단일 사용 토큰을 소비하고 저장 계층 쓰기 잠금을 획득한다.
2. 실제 루트·인덱스 핸들 및 전체 인덱스 내용, 선택 레코드, 선택 파일의 핸들 정체성·타입·크기·수정 시각·정확한 바이트를 다시 확인한다. 바이트는 기존 4 MiB 청크 비교를 재사용한다. 하나라도 바뀌면 모든 삭제 전에 거부하고 새 선택을 요구한다.
3. 시각 오름차순, 동일 시각이면 ID 순으로 대상을 정렬한다. 직렬화된 v2 정리 의도를 한도 검사하고, 기존 인덱스 핸들에 기록한 뒤 `close()` 및 재읽기 일치 확인을 완료한다. 이 확인 전에 버전 파일을 삭제하지 않는다.
4. 각 항목 직전에 현재 인덱스가 직전에 확인한 인덱스와 동일하고 같은 정리 의도를 유지하는지 확인한다. 경로를 다시 해석하여 선택 파일이 준비 당시와 같은 파일·바이트인지 재확인한다. `.filenally`와 부모 경로 핸들 바뀜도 거부한다.
5. 정확한 부모 핸들에서 해당 파일명 하나만 `removeEntry(name)`으로 제거한다. `recursive: true`를 사용하지 않는다. 직후 파일 부재를 확인한다. 삭제 메서드의 반환값만으로 성공을 단정하지 않는다.
6. 현재 인덱스가 여전히 예상한 내용인지 확인한다. 해당 버전과 `remainingIds`의 ID 하나만 제거하고 완료 수·바이트를 갱신한다. 마지막이면 `cleanup: null`로 한다. 인덱스 쓰기·close·재읽기가 성공해야 해당 항목을 **완료**로 표시한다.
7. 오류는 즉시 다음 항목 실행을 중단한다. 파일 제거는 됐지만 인덱스 갱신이 확인되지 않았다면 **복구 필요**로 표시하고 성공으로 집계하지 않는다. 인덱스 쓰기 실패를 이유로 파일을 재생성하거나 이전 인덱스를 무조건 덮어쓰지 않는다.

사용자의 중지는 청크 검증 중 또는 항목 경계에서 확인한다. 파일 삭제 호출이 시작된 항목은 부재 검사와 인덱스 갱신을 마친 뒤 멈춘다. 의도 기록 후 남은 항목이 있으면 복구 필요 상태가 남으며, 사용자가 복구 화면에서 정합성을 정리한다. 중지를 되돌리기로 표현하지 않는다.

프로세스 종료·전원 장애에 대한 보장은 브라우저가 실제 보존한 파일과 인덱스 범위에 한정된다. 두 파일 작업 사이의 상태는 복구할 수 있지만 손상되거나 외부에서 제거된 인덱스를 자동 재구성하지 않는다.

## 8. 중단된 정리의 복구

앱을 다시 열어 진행 중 의도가 발견되어도 자동 삭제·자동 인덱스 수정을 하지 않는다. 사용자가 **중단된 정리 확인**을 눌러 다음 읽기 전용 미리보기를 준비한다.

- 남은 ID 중 실제 파일이 없는 항목: 인덱스에서 제거할 기록.
- 유효한 파일이 남은 항목: 파일과 기록을 보존하고 정리 선택을 취소할 항목.
- 권한·읽기 오류, 파일 대신 디렉터리, 기록과 다른 크기, 잘못된 경로: 복구를 막는 항목.

사용자가 **기록 정합성 복구**를 확인하면 권한·루트·전체 인덱스·각 파일 존재 상태와 핸들·메타데이터를 다시 검사한다. 준비 이후 변경되었으면 쓰지 않는다. 부재를 확인한 의도 대상 기록만 제거하고, 존재하는 파일의 기록과 모든 미선택 기록은 유지한 채 `cleanup: null`인 v2 인덱스를 한 번 기록·close·재읽기 확인한다. 이 기능은 버전 본문이나 디렉터리를 삭제·작성하지 않는다.

정리 의도에 없는 누락 기록은 제거하지 않는다. 복구 후 남은 파일을 삭제하려면 새로 선택하고 다시 확인해야 한다. 미등록 파일을 인덱스에 자동 편입하거나 손상된 인덱스를 초기화하지 않는다. 파일이 없어진 이유를 앱 삭제로 추정하지 않고 **누락 기록 정리**로 보고한다.

## 9. 구성 요소와 API 경계

원본은 계속 `dev/js/file-nally.js`, `dev/file-nally.html`, `dev/css/file-nally.css` 세 개이다. 새로운 런타임 의존성·라우터·워커·서버는 추가하지 않는다. 루트 HTML은 빌드로만 생성한다.

`VersionStore`는 다음 공개 동작을 맡는다. 토큰의 내부 구조는 외부에 노출하지 않는다.

| 동작 | 입력과 결과 | 부작용 |
|---|---|---|
| `inspectUsage(root, options)` | 취소·진행 콜백, 루트별 등록/관찰 집계와 오류·완전성·복구 상태 | 읽기만 |
| `prepareCleanup(root, records, options)` | 1~100개 정규 선택 레코드, 단일 사용 준비 토큰과 표시용 요약 | 읽기만 |
| `cleanup(prepared, options)` | 준비 토큰, 취소·진행 콜백, 항목별 완료/미실행/복구 필요 결과 | 선택 파일 및 같은 루트 인덱스 |
| `prepareCleanupRecovery(root, options)` | 진행 중 의도, 단일 사용 복구 토큰과 부재/보존 요약 | 읽기만 |
| `recoverCleanup(prepared)` | 복구 토큰, 정리한 누락 기록 수와 보존 수 | 같은 루트 인덱스만 |

취소는 기존 비교와 같은 `isCancelled: () => boolean` 계약을 사용한다. UI 소유권 확인은 저장 계층에 DOM을 전달하지 않고 콜백으로 연결한다. UI 콜백 오류나 늦은 콜백이 이미 완료된 파일 작업을 중복 실행해서는 안 된다. 삭제 호출 시작부터 해당 인덱스 커밋 확인까지는 UI 진행 콜백을 호출하지 않고 항목 완료 뒤에 알린다.

공개 `capture`, `restore`, `cleanup`, `recoverCleanup`는 같은 저장 계층 쓰기 잠금을 공유하고 중복 호출을 거부한다. 복원의 내부 캡처는 잠금을 다시 획득하지 않는 비공개 경로를 사용한다. 공개 API에 잠금을 우회하는 플래그를 추가하지 않는다. 읽기 작업은 토큰과 기존 세션 검증으로 늦은 결과를 거부한다.

정리 엔진은 공개 `list`/`readVersion`의 진행 중 거부 규칙을 우회하는 공개 옵션을 만들지 않는다. 원본 인덱스 스냅샷과 정규 레코드를 검증하는 비공개 읽기 경로를 공유하되, 파일 삭제는 현재 쓰기 소유자의 정리 의도 ID와 대상 ID가 일치하는 경우에만 허용한다. 사용자에게 노출되는 진행 중 오류는 루트별 복구 필요 코드와 검증된 의도 요약을 제공하여 관리자에서 복구 진입점을 표시할 수 있게 한다.

`capture`는 기존 파일의 캡처를 시작하기 전에 기존 인덱스를 읽어 지원 스키마와 진행 중 정리를 검사한다. 진행 중 루트에 새 캡처 파일을 쓰지 않는다. 본문 기록 후 인덱스 추가를 커밋하기 직전에도 인덱스 내용·핸들이 예상과 같은지 다시 검증하며, 달라졌으면 미등록 캡처 파일은 남기고 원본 덮어쓰기를 중단한다. 그 뒤에도 기존 보관 본문·인덱스 완료 후 원본 덮어쓰기 순서를 유지한다. v2를 읽은 모든 작성자는 스키마와 정리 필드를 보존한다. 기존 호출자에 보이는 캡처·복원 반환 형식은 바꾸지 않는다.

`VersionManager`는 루트별 요약·검사 진행·복구 안내, 선택 체크박스와 선택 수, 정리·복구 확인창, 중지와 결과를 맡는다. 기존 단일 모달 자식 규칙을 확장하여 비교·복원·정리 확인이 겹치지 않게 한다. 모듈을 통째로 다른 파일로 나누는 리팩터링은 하지 않는다.

## 10. 화면과 상태

- 관리자에 루트별 등록 용량과 검사 버튼을 추가한다. 실제 검사 결과는 빠른 집계와 별도 라벨·시각으로 표시한다.
- 목록에 선택 체크박스와 선택 해제/정리 버튼을 추가한다. 첫 선택과 다른 루트의 체크박스를 잠그고 이유를 표시한다. 선택된 루트·개수·용량을 고정된 요약 영역에 표시한다.
- 준비·검사 중에는 화면을 닫거나 중지할 수 있고 쓰기는 발생하지 않는다. 닫힌 세션의 늦은 결과는 폐기한다.
- 삭제·복구 쓰기 중에는 닫기·Escape·중복 확인을 막는다. 삭제에는 안전 중지 버튼을 제공하고 현재 항목 마무리 중임을 알린다. 복구 인덱스 쓰기는 시작 후 취소하지 않는다.
- 관리자 전체가 열린 동안 기존 폴더 선택·교환·프로필 연결·설정 가져오기·동기화 잠금을 유지한다. DOM 버튼뿐 아니라 핸들러와 저장 계층 진입점에서도 검사한다.
- 사용량 조회·미리보기·취소는 동기화 계획을 무효화하지 않는다. 정리 또는 복구의 쓰기 시도 후에는 오래된 버전/사용량/선택·비교/복원 토큰을 폐기하고 새로 읽는다. 외부 원본 변경 가능성에 대비해 기존 복원과 동일하게 다음 동기화에는 새 비교를 요구하되 매니페스트·체크포인트는 변경하지 않는다.
- 결과는 현재 대화상자와 실시간 로그에 작업 ID, 보관 루트, 확인된 완료 수·논리 바이트, 실패 항목과 복구 필요 여부를 표시한다. 별도 영구 정리 이력 DB는 만들지 않는다.
- 한국어/영어, `textContent` 출력, 키보드 진입·복귀, 접근 가능한 상태 알림, 375/768/1280px 레이아웃을 유지한다. 삭제 결과의 해제된 바이트는 논리 파일 크기이며 실제 디스크 여유 공간 증가를 보장하지 않는다고 안내한다.

## 11. 검증 기준

각 독립 산출물은 실패하는 테스트부터 작성한다. 현재 279개 회귀 테스트는 출발점이며 새 기능의 검증을 대신하지 않는다.

### 사용량

- 빈 루트/인덱스 없음에서 생성·권한 요청·쓰기 시도 0회.
- 두 루트 및 같은 이름의 서로 다른 루트, 파일별 합계, 0바이트, 큰 합계의 정확성.
- 음수·비정수·안전 범위 초과 크기, 손상/중복/미지원 인덱스를 0으로 오인하지 않음.
- 등록·미등록·누락·타입/크기 불일치, 인덱스/기타 파일의 용량 분류.
- 부분 순회·한도·오류·취소·늦은 완료·인덱스 교체, 미방문 파일의 누락 오판 방지.

### 스키마와 삭제

- v1 읽기와 기존 캡처·복원의 형식 유지, 명시적 첫 정리에서만 v2 전환.
- 모든 v2 작성자의 스키마 유지, 엄격한 정리 필드·ID·크기 한도 검증.
- 준비·취소·권한 거부·혼합 루트·잘못된 토큰·101개 선택에서 쓰기 0회.
- 캡처 ID의 대소문자 별칭·비표준 문자·실제 디렉터리 이름 불일치에서 정리 거부, 기존 조회·복원 동작 보존.
- 양방향/원본→대상/대상→원본 및 폴더 교환 후에도 선택한 실제 루트에만 적용.
- 같은 크기·수정 시각의 바이트 변경, 레코드/인덱스/핸들 교체, 늦은 파일 생성·삭제·디렉터리 대체를 거부.
- 정리 의도 쓰기·close·재읽기 실패 전에는 본문 삭제 0회.
- 첫 파일과 중간 파일의 삭제 실패, 삭제 후 인덱스 쓰기·close·재읽기 실패에 후속 파일 미삭제.
- 진행 중 표식이 있을 때 캡처·복원·읽기 작업이 정해진 규칙으로 거부되고 다른 루트는 계속 조회 가능.
- 원본, `.trash`, 미선택·미등록 파일, 예상하지 못한 형제 항목의 바이트 보존 및 재귀 삭제 호출 0회.
- 마지막 보관 버전 경고, 유효하지 않은 남길 버전을 안전 사본으로 계산하지 않음, 확인 이후 보존 근거 버전의 변경·소실을 거부.
- 직접 API 중복 호출, 복원 내부 캡처, 준비 이후 다른 쓰기, 안전 중지 경계.

### 재시작·복구·화면

- 의도 게시 직후, 파일 삭제 직후, 각 인덱스 커밋 직후의 저장 상태로 페이지를 다시 열어 복구를 검증.
- 복구는 의도에 속한 누락 기록만 제거하고 존재 파일·미선택 기록을 보존. 복구 중 본문 생성/삭제 0회.
- 복구 준비 이후 파일 출현·소실·교체, 인덱스 변경, 권한 거부, 복구 쓰기 실패에서 안전한 재시도.
- 취소/닫기/재열기와 오래된 작업 완료가 새 세션의 잠금·선택·결과를 덮어쓰지 않음.
- 페이지 선택과 루트 제한, 모달 상호 배제, 경고 체크, 초점 복귀, 한·영 문구 및 3개 화면 폭.
- 모의 파일시스템의 삭제/재읽기 실패 주입을 보강하고 실제 OPFS에서도 선택 파일 삭제·인덱스 완료·재시작 복구를 검증.

검증 명령은 `docs/BUILD.md`를 따른다: `npm run build`, `npm run build:test`, `npm run build:check`, `git diff --check`, `npm test`, `npm run test:visual`. 화면 캡처는 실제로 열어 검토한다. 단계별·최종 검토에서 발견한 결함과 안전성 테스트 누락을 해소한 뒤에만 완료를 보고한다.

## 12. 후속 보존 정책과 이슈 종료

이번 산출물 검증 후 별도 보존 정책 설계에서 다음 승인된 방향을 구체화한다.

- 기본 비활성화, 사용자의 명시적 활성화, 실제 보관 루트와 원래 경로별 정책.
- 개수·기간으로 후보를 미리 보고 같은 정리 엔진으로 수동 적용한 뒤 자동 실행을 제공.
- 자동 정리는 성공한 동기화의 실제 목적지 루트만 대상. 실패·중단된 실행, 미등록 파일, 손상되거나 복구 중인 보관함에는 적용하지 않음.
- 경로별 최신 유효 버전과 해당 실행에서 만든 캡처는 자동 삭제에서 보호.
- 정책 저장의 루트 결합, 개수·기간 결합 규칙과 경계, 적용 시점·정리 오류 보고, 재연결/설정 가져오기 때 자동 활성화 금지는 그 설계에서 확정.

수동 정리만으로 #12를 닫지 않는다. 보존 정책까지 구현·검토·전체 회귀·화면 검증을 마치고, 배포 반영 여부와 플랫폼상 제외 범위를 이슈에 기록한 뒤 종료한다. 생성일·작성자·소유자·ACL과 델타 저장은 이미 합의된 제외 범위를 유지한다.

## 13. 근거와 알려진 한계

- 기존 저장 형식·실패 후 미등록 파일: `2026-09-13-version-capture-foundation-design.md`.
- 실제 보관 루트, 확인 토큰, 복원 전 캡처와 잠금: `2026-09-13-version-manager-design.md`.
- 읽기 전용 상태와 취소·스냅샷 경계: `2026-09-13-version-comparison-design.md`.
- API 근거: [WHATWG File System Standard — removeEntry](https://fs.spec.whatwg.org/#api-filesystemdirectoryhandle-removeentry). 비재귀 제거를 사용하며 삭제 결과와 부재를 별도로 확인한다. 여러 파일 제거와 인덱스 변경을 한 번에 확정하는 API로 취급하지 않는다.

인덱스·파일 재검증과 앱 내부 잠금은 독립된 다른 탭, 구버전 앱, 외부 편집기를 파일시스템 수준에서 잠그지 못한다. 동일 보관함에 대한 동시 쓰기를 지원한다고 주장하지 않는다. 최종 재검증과 실제 삭제 사이의 외부 변경 경쟁, 브라우저·운영체제 저장 실패, 손상된 인덱스 전체의 자동 복원은 보장 밖이다. 수동 정리 확인에는 영구 삭제와 별도 백업 필요성을 명시한다.
